# PromptStreak — Encryption Key Escrow (H.3)

Two keys must survive the loss of the production VPS, both operator laptops,
and any single password-manager outage. Without them, encrypted GitHub tokens
in restored backups are useless and no historical user data can be decrypted.

| Key                              | What it protects                                    | Generated by                              |
| -------------------------------- | --------------------------------------------------- | ----------------------------------------- |
| `GITHUB_TOKEN_ENCRYPTION_KEYS`   | Per-user GitHub OAuth tokens stored in the database | `apps/web/scripts/generateTokenKey.ts`    |
| Backup recovery key (age secret) | Every encrypted Postgres dump (`*.sql.gz.age`)      | `age-keygen` on a trusted laptop          |

## Storage rule (both keys, independently)

Each key is stored in **three** independent locations. Any single location can
be lost without losing recoverability.

1. **Operator A's password manager** — record name `promptstreak/<key-name>`.
2. **Operator B's password manager** — same record name, separate vault.
3. **Sealed paper envelope** in a fire-rated safe at the registered business
   address. The envelope label is `promptstreak / <key-name> / <YYYY-MM-DD>`.
   QR-encoded with `qrencode -o key.png`, printed on archival paper.

The two operators MUST use different password-manager providers (e.g. one
1Password, one Bitwarden) to remove a single-vendor failure mode.

## Generation procedure (one-time per key)

Run on a trusted laptop, fully offline if possible:

### Token-encryption key

```sh
cd apps/web
pnpm tsx scripts/generateTokenKey.ts
# Output: a base64 line. Save the WHOLE line.
```

### Backup recovery key

```sh
age-keygen -o promptstreak-backup.key
cat promptstreak-backup.key   # both lines: the comment AND the AGE-SECRET-KEY-1...
age-keygen -y promptstreak-backup.key   # public key, copy into deploy/age-recipients.txt
```

## Escrow procedure

1. Copy the secret value into both operator vaults.
2. Print the secret value AND a QR code of it onto a single A4 sheet.
3. Fold and seal in a tamper-evident envelope. Sign across the seal.
4. Photograph the sealed envelope (front and back) and store the photos with
   each operator's vault entry.
5. Place envelope in the safe.
6. Shred every digital copy on the generation laptop. Empty the trash. Reboot.

## Recovery dry run (REQUIRED before relying on escrow)

Within 7 days of escrow, both operators independently:

1. Sign in to their password manager from a clean device.
2. Read the secret. Confirm length and the first/last 6 characters match the
   value the other operator sees.
3. For the backup key: decrypt one test dump from staging
   (`age --decrypt -i <key> <file>.sql.gz.age | gunzip | head -1`).
4. For the token key: run `pnpm tsx scripts/decryptTokenSmoke.ts` (writes a
   one-off encrypted blob with the active key, then decrypts it; succeeds iff
   the active key value is correct).
5. Record the dry-run completion date in `docs/ops/key-escrow-runs.md`
   (created on first run; one row per key per quarter).

If any operator cannot complete steps 1–4, the escrow is broken — re-run the
escrow procedure before considering the system production-ready.

## Rotation

Both keys are versioned (token keys via the `KID:base64` envelope, age keys
via a new keypair + a re-encrypt pass over the backup volume). Rotation
procedure is documented separately when the first rotation is due.

## What this does NOT do

- Does not protect against a malicious operator with both vault access AND
  physical safe access. The system trusts at least one of the three storage
  locations to remain honest.
- Does not protect tokens encrypted under a key whose value has been LOST. By
  design — that is the user-data-minimization story.
